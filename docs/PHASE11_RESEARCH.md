## 4. 取舍理由

- **零新增运行时依赖**：Phase 11 只增加数据与 UI；生产包体积不应为了“看起来工程化”增加 1–6 MB 依赖。
- **校验必须业务化**：题库的安全边界不是“字段类型正确”，而是“AI 生成不得冒充真题、答案必须在选项内、材料引用存在、开放题不得自动评分”。通用 schema 库表达不了这些，仍需手写规则，反而重复。
- **状态机必须可审计**：状态转换少且需要 revision/幂等语义；显式函数比第三方机器更易测试与解释。
- **渲染安全靠结构**：所有用户文本经 `esc()`；不拼接不可信 HTML；不引入 sanitizer 作为“先 innerHTML 再洗”的借口。
- **不引入图表库**：考试页以数值、来源、状态为主，没有需要复杂图表的数据；保持可访问性与离线。

## 5. 复核触发条件

出现以下情况时重新评估依赖：

1. 题目类型扩展到需要复杂 JSON Schema 联合/递归校验；
2. 状态机超过 ~15 个状态或需要可视化；
3. 真正加入官方授权音频并需要跨浏览器音频解锁/波形；
4. 渲染必须接受用户富文本/HTML；
5. 题库规模大到需要索引/查询引擎（届时先评估 IndexedDB 索引是否足够）。

## 6. 失败与修正记录

- 最初把内置题标为 `shanghai-gaokao-foreign-language-first`，导致 2028 卡片显示“16 题”，暗示题库适用于 2028。改为 `other`（项目自编通用迁移题），规格卡不再把题目归属到未确认年份。
- 最初把 2026 春考的分值直接用于“2028 目标规格”，会让 UI 看起来像已确认；改为 2028 全 `null` + `provisional`，2026 单独一张 `official_confirmed` 卡。
- 曾考虑把 2026 官方题型分值写死（如语法 10 分），但官方页面没有公布题量/分值；放弃，避免伪造精度。
